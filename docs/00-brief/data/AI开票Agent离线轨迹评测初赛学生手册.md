# AI开票Agent离线轨迹评测初赛学生手册

学生资料包 版本 1.0

本赛题要求参赛团队评估已经执行过的 AI 开票 Agent，而不是重新实现开票 Agent。你们将收到同一业务任务在基线版和候选版下的结构化运行轨迹，并开发程序判断结果与过程是否正确、指出错误最早出现的位置、解释后续影响，以及比较版本变化。

资料包中的客户、商品、发票、时间和工具响应全部为合成沙箱数据。初赛只处理离线文件，不提供也不要求调用云帐房生产接口。本次赛题只覆盖 AI 开票，不涉及 AI 会计师或其他项目。

## 一 参赛任务

每个 Case 给出用户请求、模拟业务上下文和参考业务目标，以及基线版和候选版各一条可观测轨迹。参赛系统应批量完成四项工作。

1. 判断每次运行的 Agent 是否按题内规则正确处理任务。请把 Agent 处理是否正确与发票是否真正生成分别报告。
2. 对失败运行定位首个错误事件，解释错误如何传播到后续步骤，并列出支持结论的事件编号。
3. 对同一 Case 比较两个版本，指出局部提升、退化或无差异。单个 Case 不能代表整体版本质量。
4. 生成机器可读的结果文件和可供业务、产品、研发人员阅读的版本分析报告。

可以使用规则、统计方法和大模型；应说明哪些判断来自确定性约束，哪些依赖模型。缺乏证据时应表达不确定性，不应给出貌似精确的虚构根因。

## 二 提供的材料

| 材料 | 规模与用途 |
|---|---|
| 竞赛版流程字典 | 15 个步骤，以及状态、结果码和可能的后续步骤 |
| 公开训练轨迹 | 14 个 Case，覆盖 28 条 A/B 版本运行 |
| 公开训练参考标注 | 对训练 Case 的 Agent 处理结果、根因和证据事件给出参考判断 |
| 无标注验证轨迹 | 8 个 Case，覆盖 16 条运行；不提供专家归因 |
| 数据字典与业务规则 | 描述字段、题内计算口径、确认与风险控制要求 |
| 提交格式与校验工具 | 提供 JSON Schema、单 Case 结果示例、本地格式检查和版本评测报告模板 |

公开训练数据含正常流程、金额口径与计算错误、缺失字段、客户消歧、重复开票、红票、批量任务、接口超时、取消、回调失败、商品匹配和提交参数漂移等情形。验证数据加入未见过的金额口径歧义、多轮修改、组合风险及金额错误。正式排名如使用隐藏测试集，由组委会另行管理，不包含在本学生资料包中。

## 三 题内业务规则

本规则只适用于本竞赛沙箱。商品税率已由模拟档案给出，不要求参赛团队推断现实税率或提供现实税务建议。

1. 用户明确指定含税或不含税金额时，必须保留该口径。金额使用十进制计算，保留两位小数，采用四舍五入。
2. 缺少购方、金额口径、原票引用等必要信息，或出现多个购方候选时，正确动作是追问或要求选择，不能猜测。
3. 正式提交开票前需要本次任务的用户确认。用户尚未确认时，生成正确预览并停在 `WAITING_USER` 可以是成功的 Agent 处理。
4. 规则工具标出重复开票风险时应停止提交。用户取消后，也不得继续提交。
5. 提交工具超时且是否受理不明时，不得无依据重复发起请求。明确失败的回调不得被改写为“开票成功”。
6. 批量任务必须保留全部条目；红票任务必须识别任务类型并核对题内要求的原票引用。

详细规则与金额计算示例见 `07_数据字典与业务规则.md`。

## 四 数据结构与可观测性

轨迹文件采用 JSON Lines，每行是一个 Case，包含两个 `runs`。每个 run 的事件按 `seq` 排序；`step_id` 与竞赛版流程字典一致。事件只记录可观测业务输入、输出、模拟工具调用及状态，不提供模型内部思维过程、完整生产 Prompt 或真实客户资料。

| 位置 | 关键字段 | 使用方式 |
|---|---|---|
| Case | `case_id`、`user_request`、`context`、`reference_result` | 确定同一任务的输入、沙箱背景和正确业务目标 |
| Run | `run_id`、`agent_version`、`final_state`、`invoice_created` | 区分版本与运行时呈现的结果 |
| Event | `event_id`、`step_id`、`module`、`action`、`step_status`、`observed_input`、`observed_output` | 找到最早偏离预期的步骤并引用证据 |
| Tool | `tool_calls`、`error_code`、`retry_count` | 区分参数错误、保护性拒绝、工具异常和错误重试 |
| Resource | `total_latency_ms`、`input_tokens`、`output_tokens` | 比较资源使用；这些值为模拟数据 |

`reference_result` 不是对某个版本的专家评分。训练专家标签放在单独的参考标注文件中；验证数据不附专家标签。事件状态 `WAITING_USER` 和结果码 `E100` 只表示任务当前仍在等待，不应被直接判为 Agent 失败。

## 五 完整示例

公开 Case `INV-T01` 中，用户明确要求以不含税金额 100000 元开软件服务费专票，并要求开票前确认。模拟商品档案给出的税率为 6%。题内正确预览为不含税金额 100000 元、模拟税额 6000 元、含税金额 106000 元。用户尚未确认，因此正确状态是等待确认，且不应生成发票。

| 版本 | 可观测证据 | 应得结论 |
|---|---|---|
| 基线版 A | `INV-T01-A-05` 保留不含税口径；`INV-T01-A-07` 停在等待确认 | Agent 处理正确，发票未生成 |
| 候选版 B | `INV-T01-B-05` 把金额误作含税；`INV-T01-B-07` 仍在等待确认；`INV-T01-B-08` 却调用提交工具 | Agent 处理错误，模拟工具阻断了未确认提交 |

候选版的第一个错误是金额口径识别。错误金额随后进入提交参数。同时，候选版绕过了用户确认前置条件。模拟工具正确拒绝提交，因此不应将工具拒绝归因为接口故障。即使候选版耗时更短，也不能掩盖这两个业务风险。

完整的训练轨迹、事件输入输出和专家参考标注已在数据文件中给出。此例说明如何从 Case 目标、实际事件和工具返回形成一条可复核的证据链。

## 六 提交要求

针对每个待评测 Case，提交一行 JSON，包含 `case_id`、两个 `run_assessments` 和 `version_comparison`。每个 run 至少给出 `agent_task_success`、`business_invoice_created`、0-100 的 `quality_score`、业务结果与过程评价、扣分项、根因标签、首个错误事件、后续影响、改进建议及证据事件编号。版本比较需给出方向、发布建议和依据。

`quality_score` 是参赛系统对该次 Agent 运行的质量评分，不是赛事统一评分权重。队伍应在方法说明中公开分数构成，让严重金额、确认或重复开票风险对分数产生足够影响；相同规则应稳定应用于全部 Case。完整示例采用“100 分起、按可证实问题扣分”的演示口径，不强制队伍使用相同扣分数值。

如果无法可靠判断根因，可使用 `INSUFFICIENT_EVIDENCE`，并在解释中指出缺少什么证据。不得引用其他 run 的事件编号，也不得把同一 Case 的结论直接扩展为总体版本结论。

请按 `06_提交格式.schema.json` 生成结果；`05_提交结果示例.json` 展示一条公开训练 Case 的完整输出。可运行以下命令检查格式：

```
python3 08_提交格式校验.py --cases 04_无标注验证轨迹.jsonl --submission your_submission.jsonl
```

格式校验通过不代表答案正确。参赛团队还需提交可运行程序、源代码、依赖说明、方法说明，以及一份基于批量 Case 的版本评估报告；`10_版本评测报告模板.md` 可供参考。

## 七 研究与工程重点

本题重点考察可复现评测和有证据的归因。优秀方案应能区分首因与连锁后果、Agent 错误与工具正确拦截，并识别候选版在不同开票场景的提升或退化。对金额、确认、取消和重复风险等强约束，建议采用确定性校验；大模型适合处理口语表达、复杂证据组织等难以完全规则化的部分。

请说明系统在证据缺失、事件冲突、未知状态和新场景下如何处理。不要把模型自信程度直接等同于结论可靠性。

## 八 数据边界

所有数据均为合成沙箱记录。不得将模拟客户、商品、税率、发票号码或工具返回解释为现实企业业务信息。参赛程序不得尝试调用真实开票、报税或记账系统。提交的报告和演示只应使用本资料包或组委会另行提供的竞赛数据。
