## 一句话

**Jev 是 TypeSafe AI 发布的 "System One Model"：刻意不做文本生成，只返回类型化的概率决策。**
它不回答"说一段话"，只回答程序能直接分支的三种问题：**选哪个 / 打几分 / 是不是**。

---

## 一、三种原语（外部事实）

| 原语 | 中文 | 输出形态 | 官方给的适用场景 |
|---|---|---|---|
| `choice` | 单选题 | 选项 + 每项概率 + confidence | 工具路由、动作选择、**分类** |
| `score` | 打分题 | 连续分数 + 概率分布 + confidence | 风险评分、**质量评分**、相关性 |
| `noul` | 判断题 | 0–1 概率 | 是否保留 / 是否危险 / **是否达成目标** |

**与「大模型 + JSON Schema」的差别**（来源作者强调）：不是"能不能返回 JSON"——现在通用模型都能返回结构化输出。真正的差别是 **Jev 从设计上放弃了自由文本生成**，输出空间是封闭的，所以它可以只做一次前向、返回校准过的概率。

**定位比喻**：不是 Agent 的**大脑**，是 Agent 的**反射神经**——放在内部处理"输出空间固定、调用频率高、需要一点语义理解"的小判断。

**明确不适合**：写文章、解释复杂代码、长链路规划、跨文件多步推理。

---

## 二、两个容易被误读的宣传点

| 宣传说法 | 更准确的说法 |
|---|---|
| "不会幻觉" | 它**不会输出 schema 之外的东西**（类型安全），但**仍然可能选错**——类型安全 ≠ 语义正确 |
| "概率可信" | 概率校准是核心卖点，但**公开的校准数据与训练细节不足**；工程上必须先用自己样本做 shadow mode，再定自动执行阈值 |

来源作者给的工程纪律：先 shadow mode 跑一段 → 用自己的业务样本统计不同概率段的真实正确率 → 再定阈值 → 高风险场景保守处理。

## 三、开源现状：**模型本体没有开源**

- **没有权重、没有训练代码**。TypeSafe 是商业闭源模型。
- GitHub 上的 Jev 相关仓库分三类：

| 类别 | 代表 | 说明 |
|---|---|---|
| **接口复刻** | `ollaya-dev/ollaya` | 用开源判定模型在本地服务出 **wire-identical 的 Jev API**（`/v1/systemone`），TypeSafe SDK 改 base_url 即可用 |
| **生态工具** | `tamaratran/fast-jev-compaction`（上下文压缩）· `PyModel/jev-judge-mcp`（MCP 判定工具）· `realZachi/pg-jev`（PostgreSQL 扩展）· `devagrawal09/jev-review`（代码审查） | 把"判断"从生成链路里拆出来的各种落点 |
| **索引/对照** | `yibie/awesome-jev`、`v-modal/awesome-jev-tools` 等 | 社区整理的目录站；**数量会漂，本文不记计数** |

**效果对照（ollaya README 自报，as of 2026-10-31）**：开源复刻 `winnow:e4b` 在 typed decisions 上 **0.724**，TypeSafe 官方 Jev **0.738**。
⇒ **开源复刻在"判得准"上并不占优**；它的意义是**本地、免费、可自托管**。
⇒ 判定模型相对通用模型的优势不是准确率，而是 **延迟（毫秒级）、成本（高频摊薄）、输出可进代码分支**。

## 四、与本题 schema 的结构对照（纯结构，不含取舍）

对照对象：`docs/00-brief/data/06_提交格式.schema.json`

| Jev 原语 | 本赛题里形状相同的字段 |
|---|---|
| `noul`（0–1 概率） | `agent_task_success`、`business_invoice_created`（布尔） |
| `choice`（枚举 + 概率） | `root_causes[].label`（**14 个固定枚举**）、`version_comparison.direction`（4 值枚举）、`release_recommendation`（4 值枚举）、`penalty_items[].dimension`（4 值枚举） |
| `score`（连续分 + 分布） | `quality_score`（0–100）、`penalty_items[].points_deducted` |
| confidence（0–1） | `root_causes[].confidence`（schema 里已有该字段） |

**一个结构观察**：该 schema 的输出空间几乎全是**封闭枚举 + 概率/分数**，这与 Jev 的三种原语高度同形。
**但这只是"形状相同"，不构成"应当使用"的理由**——见下节。

## 五、为什么不构成本期工作项（**成本事实，不是决策**）

| 维度 | 事实 |
|---|---|
| **调用量级** | 本赛题训练 14 Case + 验证 8 Case；即使每 Case 追问十余次，总量在**数百次**量级。社区选型经验：每小时几十次 → 通用大模型就够；**每天数十万次**判定的场景，判定模型才明显划算 |
| **时间** | 初赛截止 **2026-11-13**；学习新运行时 + 校准阈值的时间成本高 |
| **准确率** | 开源复刻 **0.724 < 官方 0.738**，且未见第三方在"轨迹归因"这类任务上的校准报告 ⇒ **不能假设它比通用模型判得更准** |
| **依赖面** | 需要额外运行时 + 模型权重（GB 级下载）＋ GPU 或 CPU 推理；引入一个新的失败面 |
| **评审关注点** | 手册「研究与工程重点」强调的是**可复现评测**与**有证据的归因**，不是推理延迟 |

> ⚠️ 这五条只是"当前不值得作为工作项"的**成本依据**。**要不要用、用在哪，属 `10-spec`/`20-design` 的决策范围，本文不做。**

## 六、可借鉴的设计点（**只记录，不落地**）

这几条独立于"是否引入 Jev"，属于接口/判据的设计范式：

1. **一个问题只做一个判断**——不要问"是否还重要？如果重要请决定是否截断"（混了多个判断）；拆成两个窄问题。
2. **概率进代码分支，不进解释文本**——`if p >= 0.8: 自动 / 0.5–0.8: 保守 / <0.5: 回退`，而不是让模型写一段"我建议保留"。
3. **三态而不是二值**——`是 / 否 / 证据不足`，与本题 `INSUFFICIENT_EVIDENCE` 同构。
4. **"不改写、只删除"的压缩路线**——`fast-jev-compaction` 的立场：摘要会改写事实（文件路径、错误码、命令参数最容易被"概括掉"），所以它**只删工具调用/结果、保留原样**，用户与助手文本逐字不动。这条对"证据必须可回指 `event_id`"的赛题语境有参考价值。
5. **降级链要显式**——它的 `state` 预算是逐级降级的（先削细节、再删内容；先旧后新），每一级都可观测。

## 七、若要试点，可能的落点（**未决策，仅列位置**）

- `30-tdd` 要画的"确定性 vs 模型"边界里，**模型那侧**目前是通用大模型；判定模型是这一侧的另一种实现选项。
- 语义类根因（`ENTITY_RESOLUTION` / `PRODUCT_MATCH` / `INTENT_CLASSIFICATION` / `CONTEXT_UPDATE`）是规则最难覆盖的部分，属"输出空间可枚举"的典型。
- **前置条件**：必须先有 `10-spec` 的判据与 `30-tdd` 的对应用例，否则试点无法评估。
