## 二、三个想法的价值评估（深度 × 广度 × 可验证性 × 成本）

| 想法 | 深度（解决了什么真问题） | 广度（覆盖范围） | 可验证性 | 估时 |
|---|---|---|---|---|
| **影响封顶** | 高：把"实际后果"与"违规标签"解耦，同一标签下区分"只错预览"与"错票真的开出去" | 中高：14 类根因中的 5 类封顶场景 | **高**：封顶触发/不触发可用正反控核对 | **0.5–1 天** |
| **五维 Rubric** | 中：扣分从"标签→分值"改为"维度→分值"，可解释性更好，但不改变结论（双轨） | 中：14 类根因全映射 | 中：需与人工评分做一致性校验 | **2–3 天**（含双轨） |
| **反事实最小修复** | 高：回答"首因 vs 传播"、"独立根因"、"责任对象" | **低**：仅覆盖"可重算字段"，`GUARD` 边原则上不可模拟 | 中：设计给了 4 个试点 Case（T01/T05/T10/T14） | **5–8 天**（tier-1 约 2–3 天） |

**按"每投入 1 天能提升多少评分维度"排序：影响封顶 > 五维 Rubric > 反事实。**

## 三、因果分析：设计为什么有价值、风险从哪来

### 3.1 现有评分的因果缺陷（所有设计的起点）

当前 `quality_score = max(0, 100 − Σ固定扣分)`，扣分只取决于**根因标签**（50/30），与"错误是否真的造成后果"无关：

- `INV-V01-B`：自拟口径、未追问 → 扣 30 → 70 分，但**发票未生成**；
- `INV-V14-B`：提交漂移且**已开票** → 扣 30 → 70 分，**错误发票已实际开出**。

两者**同分**，业务后果差一个量级 ⇒ 分数无法独立支撑"哪个版本更该推荐"，版本方向只能靠布尔值兜底。

### 3.2 影响封顶为什么能补这个洞

它引入的是**可观察事实**（`invoice_created=true`、`user_confirmed=false`、`DUPLICATE_INVOICE` 被忽略…），不是主观判断 ⇒ 可机械判定、可写正反控、不违背 ADR-001 的"确定性内核"。

### 3.3 反事实为什么贵（贵在工程量，不在概念）

1. **字段级权威来源**：每个可修复字段须声明"用谁的值重算"（`reference_result` / 工具返回 / 已确认预览）；
2. **拓扑重算**：修复一个字段需按 `seq` 向下游传播，且不得反向修改早期事件；
3. **副作用处理**：修复可能**制造新 finding**（设计已用 `new_finding_ids` 承认），须规定不写回真实根因；
4. **覆盖上限**：`GUARD` 类边（确认、重复风险、回调）**原则上不可模拟** ⇒ 天然只能覆盖"数据类"错误。

### 3.4 双轨（ADR-006）为什么把风险压住

正式 `quality_score` 不变、官方 schema 不变、回滚=删字段 ⇒ **做了不加分、做错也不扣分**。因此反事实的合理位置是"设计+后续工作"，而非"5 天内硬做完整版"。

### 3.5 时间因果

5 天里还有最终打包、演示材料、提交前自查。**每多一个未完成模块，边际收益为负**——评审看到"设计写了、代码没有"，比"只写后续工作"更伤，因为会被读成"没做完"。

## 四、必须先补的缺口（按阻塞程度）

| 级别 | 缺口 | 为什么阻塞 |
|---|---|---|
| **P0** | **聚合公式**：封顶与维度扣分同时出现时的计算方式（例：错误金额实际开票 → 封顶 20，但金额维度本身可能扣 30） | 文档 `§十 尚未决定` 自列此项。**没有它 `rubric_score` 不可计算** |
| **P0** | 封顶是否影响 `agent_task_success` | 若影响，违背 ADR-006"不改变正式布尔值" |
| P1 | `rubric_score` 是否进入官方 submission | ADR-006 标"待定"；**冻结前必须定**，否则 schema 变动 |
| P1 | 双轨分差的可解释性验收 | 否则出现无法解释的 10–20 分差异 |
| P2 | `FIELD_FABRICATION` 的字段感知映射（金额/原票 vs 客户/商品） | 影响维度归属，不影响可行性 |
| P2 | 与人工评分的一致性阈值 | 校准项，不阻塞初赛 |

> 建议：**P0 两条必须给出"最小但可计算"的答案**，例如 `rubric_score = min(Σ维度得分, 100 − 封顶扣分)`，并明确"封顶只减分、不改布尔"。

## 五、时间账与产能估算（11-08 晚 → 11-13）

### 5.1 工作量估算（代码 + 测试）

| 模块 | 代码量估 | 测试量估 | 硬依赖 |
|---|---|---|---|
| 影响封顶 | ~200 行 | ~150 行（5 条规则正反控） | 聚合公式（需人工拍板） |
| 五维 Rubric 双轨 | ~300 行 | ~200 行（映射+校准） | 维度权重 / 是否进 schema（人工） |
| 反事实 tier-1（金额三元组 + 预览→提交复制） | ~400 行 | ~250 行（4 试点 Case 对比） | 字段权威源映射（领域判断） |
| 反事实 tier-2/3（完整版） | 再 ~400 行 | 再 ~400 行 | 同上 + `GUARD` 边界确认 |

**合计**：tier-1 版本约 **900 行代码 + 600 行测试**；完整版约 **1,700 + 900**。按两人两 agent、4 个开发日（第 5 天留给打包/演示/提交），**代码产能充足**。

### 5.2 真实瓶颈（按严重度）

| 级别 | 瓶颈 | 为什么 token 无限也解决不了 |
|---|---|---|
| 🔴 | 聚合公式未定 | AI 能写十种公式，**选哪一种属产品决策** |
| 🔴 | 反事实语义正确性不能自证 | `RECOMPUTE`/`COPY`/`GUARD` 的划分是领域判断；写错时**结果看起来对、结论反了**，比崩溃更危险。验收要求的 4 个 pilot Case 对比**必须人工看** |
| 🟡 | 双轨分差解释 | 差异需逐条回看 22 个 Case，由公开维度+`event_id` 解释 |
| 🟡 | 合并协调 | 两人两 agent 并行改同一仓库，需提前划定文件边界，否则冲突返工 |

### 5.3 两张时间表（2 agent 并行）

**激进版（三项全做，反事实仅 tier-1）**

| 天 | Agent A | Agent B | 人工 |
|---|---|---|---|
| D1 | 聚合公式落定 + 封顶实现 | 五维映射表 + 双轨骨架 | **拍板公式** |
| D2 | 反事实引擎骨架（tier-1） | 五维实现 + 校准 | 审 tier-1 字段权威源 |
| D3 | 反事实 4 pilot Case 对比 | 双轨全量 + 分差解释 | **看 4 个 Case 结论** |
| D4 | 集成进 `verify.py` 第 5 阶段 | 双轨报告 + 全量回归 | 验收 |
| D5 | 打包 / 演示 / 自查 / 提交 | 同左 | 提交 |

判断：**代码完成概率约 70–80%**；**"能交付可信结论"概率约 50–60%**（反事实为最可能拖垮的一环）。

**稳健版（封顶 + 五维，反事实只保留设计）**

| 天 | 内容 |
|---|---|
| D1 | 拍聚合公式 + 封顶实现 + 正反控 |
| D2–D3 | 五维 Rubric + 双轨输出 + 校准 |
| D4 | 集成 `verify.py` 第 5 阶段 + 全量回归 |
| D5 | 双轨报告 + 打包 + 演示 + 提交 |

判断：**完成概率约 95%**，且完全落在 ADR-006 安全边界内。

### 5.4 若选择全做，三条硬约束

1. **反事实只做 tier-1**（金额三元组 + 预览→提交复制）；tier-2/3 明写"未实现"。**不得半做 tier-2**——半实现的字段依赖最难验证。
2. **D3 结束为死线**：4 个 pilot Case 若未完成人工核对，立即砍掉反事实，代码保留并标 `experimental`。
3. **D4 全量回归必须全绿**：102 个现有测试一个不能红；红则回滚，不带病上线。

## 七、若选 A 或 B 的验收清单（可机械核对）

1. 封顶规则每条配 1 个正控（该封顶）+ 1 个负控（不该封顶）；
2. 14 Case / 28 run 双轨跑通，**方向与现有 `quality_score` 结论一致**（不一致须逐条解释）；
3. `outputs/` 产出对比表：旧分 / 新分 / 是否触发封顶 / 触发依据 `event_id`；
4. 官方 `submission.jsonl` 字段级 diff 为空（schema 不变）；
5. 方法说明新增一节，写明"为什么正式分不切换"（对应 ADR-006）。
