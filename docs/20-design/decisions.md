# 决策记录（ADR）

> 状态：ADR-001、ADR-002、ADR-003、ADR-004 已记录。

## ADR-001 确定性校验与模型判断的边界

- **日期**：2026-11-03
- **背景**：自动评估AI开票Agent的系统（判断处理结果与发票真实性、定位错误并解释、比较版本质量、生成版本分析报告）
- **候选**：
  1. 纯 LLM 判断
  2. 纯确定性规则
  3. 确定性内核 + 可关闭的 LLM 增强
- **决定**：采用方案 3 作为后续架构方向；MVP 使用方案 2，LLM 默认关闭且不是运行依赖。
- **理由**：金额、确认、取消、重复风险等强约束必须稳定可复现；LLM 只适合在证据已结构化的前提下补充语义理解和文字组织。
- **确定性代码负责**：解析事实、流程白名单、金额与税额、确认前置、取消与重复风险、工具结果分类、`agent_task_success`、`business_invoice_created`、证据有效性、`quality_score` 和 A/B 比较。
- **LLM 可以负责**：在后续增强阶段，基于规则层提供的候选问题和同一 run 的真实事件，辅助复杂语义判断、根因候选选择和解释起草。
- **LLM 不能负责**：计算或修改金额和税额；改写流程事实；直接决定两个布尔结论或 `quality_score`；生成或替换 `event_id`；绕过强约束；用单个 Case 推导整体版本结论。
- **程序校验**：模型只能引用输入中已经提供的事件编号，所有证据必须真实存在且属于当前 run；模型提出的候选根因必须与业务规则和事件证据相容。校验失败时丢弃该候选，或按后续 T-014 的口径降级为 `INSUFFICIENT_EVIDENCE`。
- **失败与降级**：LLM 不可用时，系统仍须仅凭确定性规则生成符合 schema 的输出，使用固定模板组织说明；无法可靠判断的部分输出 `INSUFFICIENT_EVIDENCE`。
- **人工边界**：人工可以参与训练集校准、抽查和报告审阅，但不能成为批量评测运行时的必需步骤。
- **代价**：后续 LLM 增强会增加模型依赖、调用成本和校准成本；MVP 不接受这些依赖。
- **回滚**：通过配置关闭 LLM，回到已经验证的纯确定性基线；关闭模型不得改变确定性规则的输出。

## ADR-002 `quality_score` 的构成

- **日期**：2026-11-04
- **背景**：需要让同一 Case 的评分稳定可复现，同时区分 Agent、工具、用户和外部服务的责任。
- **候选**：
  1. 按最终失败、开票结果直接扣分
  2. 基于已验证 Agent 根因的责任感知扣分账本
  3. 使用反事实最小修复计算信用和贡献
- **决定**：MVP 采用方案 2；方案 3 保留为候选，不进入当前实现。
- **理由**：方案 2 能让每条扣分回指真实 `event_id`，避免把工具正确拦截或外部失败归责 Agent；方案 3 复杂度更高，尚未证明普通时序归因存在需要修复的漏判。
- **扣分口径**：从 100 分开始，每个已证实且责任对象为 Agent 的独立根因按严重度扣 50 或 30 分，最低为 0；传播事件和布尔结论不重复扣分。完整映射见 [`10-spec/spec.md`](../10-spec/spec.md)「质量评分与责任分配」。
- **证据不足**：不生成 penalty；不可评分时以 `quality_score=0` 作为 schema 哨兵，排除批量均值并标记不可比较。
- **代价**：固定权重无法表达复杂的部分责任，也无法计算精确贡献比例。
- **回滚**：保留已验证根因和证据，只调整确定性 severity 映射并重算分数，不改变事实判断。
- **2026-11-04 修订**：`FIELD_FABRICATION` 由「普通错误 30」上调至「严重 50」。依据＝官方手册要求「让严重金额、确认或重复开票风险对分数产生足够影响」，而 `INV-V03-B` 在题内未提供金额时编造 100000 曾被判 70 分（偏轻）。该严重度适用于所有 `FIELD_FABRICATION`，原因是任何关键字段编造都可能产生不可追溯的业务结果，不只为金额子场景特设。

## ADR-004 反事实信用分配的进入时机

- **日期**：2026-11-04
- **背景**：已有反事实最小修复与对象感知信用分配的候选设计，需要明确是否阻塞基础评测 MVP。
- **候选**：
  1. 立即进入 B1/B2 主链路；
  2. 完全不记录该方向；
  3. 保留设计与边界，待确定性基线和训练集回归后再决定是否试点。
- **决定**：采用方案 3。反事实设计可以继续完善，但不进入基础 MVP；只有完成 T-010 训练集回归并发现至少两个真实“首因/传播难区分或重复归因”问题后，才评估实现。
- **理由**：赛题核心是可复现评测和有证据归因，首因/传播基础规则尚未用完整训练集证明不足；提前实现会增加字段依赖、修复来源和反事实副作用的失败面。
- **允许范围**：试点只作用于内部归因与 `downstream_impact`，不改变官方 schema、两个布尔结论、真实轨迹、`invoice_created` 或评分规则。
- **代价**：基础 MVP 暂时不能解释“修复哪个字段会消除多少下游 finding”，只能使用当前确定性传播链。
- **回滚**：反事实分析保持独立模块和关闭开关；关闭后必须完全回到已验证的确定性基线。
- **2026-11-04 门槛达成（留痕）**：已记录三例真实归因问题（`INV-V03-B` 编造金额漏判、`INV-V01-B` 口径自拟漏判、`INV-V03-B` 重复归因）⇒ ADR-004 的试点前置条件成立。经霖 2026-11-04 决定：**本版只做定性版**（依赖链写进 `downstream_impact` 与方法说明），完整引擎不在初赛范围。


## ADR-003 是否使用外部 LLM／用哪家

- **日期**：2026-11-04；2026-11-07 修订
- **背景**：确定性 v0.2.1 已作为正式基线；决赛前需要验证可控的 AI 技术应用，但不能破坏可复现主链路。希望同时支持云端 API 与本地 Ollama。
- **候选**：
  1. 保持完全不接入
  2. 用 LLM 直接参与正式评分
  3. 增加与正式评测解耦的可选 LLM 独立盲审
- **决定**：采用方案 3。正式 `evaluate` 命令继续完全由确定性代码生成 submission；新增独立 `audit` 命令做 LLM 盲审，输出 `llm-review.jsonl`。
- **输入边界**：盲审只能读取原始 Case、A/B run/events/tool_calls、`reference_result`、流程字典和业务规则；不得读取确定性评测结果、训练专家标签、人工结论或其他 Case 答案。
- **输出边界**：盲审输出独立记录两个布尔判断、根因候选、首错、证据、版本方向和不确定点；不计算正式 `quality_score`，不修改 `submission.jsonl`。
- **模型接入**：使用 OpenAI-compatible `/chat/completions` 接口，同一客户端支持云端 API 和本地 Ollama；端点和模型由环境变量或 CLI 显式指定。
- **可复现控制**：固定 `prompt_version`、模型标识和 `temperature=0`；记录模型与 Prompt 版本，不记录 API Key。默认 HTTP 超时 60 秒，请求失败直接报错，不生成伪造降级结论；正式确定性 CLI 不依赖模型。
- **密钥边界**：API Key 只从环境变量读取，不提供 CLI 参数，不写入日志、错误、测试或 Git；Ollama 可无 Key。
- **程序校验**：输出必须包含准确的两条 run；根因必须来自官方枚举；所有证据必须真实存在并属于对应 run；非 `INSUFFICIENT_EVIDENCE` 根因必须有有效首错事件；校验失败即拒绝该模型输出。
- **三方比较**：人工判断、LLM 盲审和确定性评测只做案例级差异检查，不采用多数投票，也不把三方一致解释为隐藏集准确率。
- **理由**：该方案可以展示 AI 技术应用和独立复核能力，同时保留 v0.2.1 作为无模型、可复现的安全回退。
- **代价**：增加模型配置、网络、成本和输出稳定性风险；因此不进入正式评分主链路。
- **回滚**：删除或禁用 `audit` 命令即可；`evaluate`、v0.2.1 包和现有 submission 输出不受影响。
